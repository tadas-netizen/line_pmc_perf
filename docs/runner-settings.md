# Runner settings

Generated by `python3 tools/runner.py --settings-md > docs/runner-settings.md` (`npm run settings-md`) from the
settings table in `tools/runner.py` — edit there, then regenerate. The runner page shows the
same text (each field's default under the input; full explanations in "What do these
settings mean?").

**PASS/FAIL** for every load scenario is exactly two conditions over the whole run (ramp up +
hold + ramp down): **p95 ≤ 300 ms** and **error rate < 1 %**, where a response slower than 1 s
counts as an error (lib/thresholds.js GATE; PERF_GATE_P95 / PERF_GATE_ERR / PERF_GATE_SLOW_MS override it). Everything else is reported only.
Empty field = the script's default (shown below). Durations: `30s`, `5m`, `1m30s`.

## Smoke

One pass, no load. Strict: every check must pass and no request may fail — it proves the SCRIPT and the environment work, not performance. Run it before any load run. The write sections create data (one order, perf products / codes / a partner / a user, images).

|---|---|---|
| **Sections** (`PERF_SMOKE_SECTIONS`) | all (the page pre-fills all; the script alone defaults to public,auth,neg,ts01) | Which parts to exercise: public = GET /api/products, POST /api/discount/validate, GET /api/product-image; auth = login as every configured role + logout; neg = no cookie → 401, viewer write → 403, out-of-scope partner → 403, inactive account → 401; ts01 = every TS-01 READ endpoint once; order = ONE real order with a slip; writes = every TS-01 WRITE endpoint once. ## TS-All

A launcher, not a new load test: runs TS-01 Endpoint (Group Run) for all 36 endpoints (reads → auth → writes, 60 s apart; the two heavy unbounded reads are left out), then TS-02 Storefront, TS-03 Admin orders and TS-04 Dashboard, with a gap between each. Every TS uses its OWN default settings; the shared settings are the load shape (ramp up / hold / ramp down, default 30s / 5m / 30s) and the TS-01 rate (one TPS for every read endpoint, one for auth, one for writes). With everything included at the default shape this takes ≈ 4 h (TS-01 alone ≈ 3 h 40 min). A failing TS does not stop the sequence. All results share this run's id. Write parts create data (orders, perf products / codes / partners / users).

## TS-01 Endpoint

Tests ONE endpoint on its own. Target mode: one rate, PASS/FAIL over the whole run (ramps included). Ladder mode: several rates, reports the highest that stays within the gate. The admin cookie is obtained once in setup() (bcrypt) and shared by every VU. Write endpoints create or change a document per request (the per-VU fixtures they act on are created once, inactive).

| Setting | Default | What it does |
|---|---|---|
| **Endpoint** (`PERF_ENDPOINT`) | admin.orders.list | Any entry from lib/endpoints.js. read = repeatable, consumes nothing (heavy = the unbounded admin-orders reads, every order in scope per request). auth = the bcrypt login. write = creates or changes data on every request (see what each leaves behind in the list). |
| **Rate (TPS)** (`PERF_RPS`) | the endpoint's own default (docs "List Load Test": 50 admin orders / products / dashboard, 10 orders, 20 other reads, 5 writes, 2 bcrypt calls, 1 heavy reads) | The fixed arrival rate for the endpoint, in TPS (HTTP requests per second). k6 starts requests at this rate regardless of how fast the server answers. Leave empty for the endpoint's default (lib/endpoints.js `rate`, from the docs' priority lines). Ignored when Ladder steps is set. |
| **Ladder steps** (`PERF_STEPS`) | none — target mode (one rate) | A comma-separated list of rates. Each step ramps up and holds for the Hold time and is judged on its own window (its ramp + hold); the result is the highest step within the gate ('capacity'). | **Max VUs** (`PERF_MAX_VUS`) | auto: rate × 1 + 5 (read), × 2 + 5 (auth), × 3 + 5 (write), × 10 + 5 (heavy) | k6 adds VUs as needed to keep the rate; this caps them. Raise only if the run reports dropped iterations. |

The quick pick "no DB write" leaves out everything that creates or changes data.

## TS-02 Storefront

Each iteration = one customer: GET /api/products?partner= → with probability P a POST /api/discount/validate → POST /api/orders (multipart: payload + slip). ≈ 2.3 requests per order, so 10 orders/s ≈ 23 TPS. Orders are spread round-robin over every orderable partner, because the order number is a Firestore transaction on one counter document per partner-month (docs §3.1.1) — one partner alone is a contention test. Every order creates a real order document and uploads a slip to GCS.

| Setting | Default | What it does |
|---|---|---|
| **Orders/s** (`PERF_ORDERS_PER_SEC`) | 10 (≈ 23 TPS) | Orders placed per second across all partners. k6 starts a new customer at this rate whatever the server's speed. TPS ≈ orders/s × 2.3 with the other defaults. The docs' line #1 is 10 TPS on POST /api/orders. |
| **P(discount code)** (`PERF_P_VALIDATE`) | 0.3 (30 % of orders) | Probability (0–1) that the customer validates a referral code (POST /api/discount/validate, public) before ordering; when it is valid the order carries it. |
| **Partners** (`PERF_PARTNERS`) | every partner with an orderable product | Limits the storefront to these partner codes (comma-separated). Empty = every partner that has an active, in-stock product in GET /api/products. One partner = one order counter = a contention test. |
| **Max VUs** (`PERF_MAX_VUS`) | auto: orders/s × 4 + 5 | k6 adds VUs as needed to keep the rate; this caps them. An order iteration lasts ≈ 1–3 s (the upload is the long call). Raise only if the run reports dropped iterations. |
| **Ramp up** (`PERF_RAMP`) | 30s | How long the load takes to climb from zero to the target. Requests during the ramp COUNT toward PASS/FAIL (they are tagged stage=ramp-up for the charts). Formats: 30s, 2m, 1m30s. |

## Soak

ONE request per iteration, drawn from the docs' priority lines by weight (PERF_MIX: order 10 · products 50 · admin orders 50 · dashboard 50 · admin products 10 → 170 TPS reproduces the table exactly), for a long hold, to find slow degradation. ≈ 6 % of the requests place real orders.

| Setting | Default | What it does |

## Stress

Steps up the priority mix by +50 TPS (50, 100, … up to the top). Each step ramps then holds and is judged on its own window. Stops at the first step that breaks the gate (p95 or errors, judged 30 s into the step). Result: the highest step within the gate, plus where p95 crossed the gate and 500 ms. Can degrade the environment and places ≈ 6 % of its requests as real orders — run last. Up to ~1 h 50 min at the defaults.

| Setting | Default | What it does |
|---|---|---|
| **Top (TPS)** (`PERF_STRESS_MAX`) | 1000 TPS (20 steps) | The ladder goes 50, 100, 150 … up to this value. Lower it to shorten the run. |
| **Step (TPS)** (`PERF_STRESS_STEP`) | 50 | The TPS added at every step. |
| **Hold per step** (`PERF_STRESS_HOLD`) | 5m | Each step holds this long and is judged on its own window (its ramp + hold). |
| **Mix** (`PERF_MIX`) | order:10,products:50,orders:50,dashboard:50,catalog:10 | See Soak. |
| **Ramp per step** (`PERF_RAMP`) | 30s | How long each step takes to climb to its rate; counts toward that step's window. |

## Spike

## Sign-in

Logins at a constant, low rate (default 2/s), alternating the configured accounts. Each call hashes the password (bcrypt cost 12, ~100 ms of CPU on the function): the point is what a login costs, not a ceiling — docs §3.2 says never to drive it as throughput.
